# LAMP 열 전체 입력을 소수 행 opening으로 바꾸는 연구의 정확한 범위

**연구 전용:** 이 기록과 `crypto/columnrs*`, `crypto/column_grid_oracle.go`는 `research/sparse-column-openings` 브랜치에서만 사용한다. LAMP 메인 구현이나 논문용 수치에 반영하지 않는다. KZG 행렬 증명은 이 브랜치의 설계가 아니다.

## 원래 의도

기존 LAMP의 Groth16 회로는 표본 열 `j`마다 A/B/C의 길이 `K` 열벡터를 witness로 받아 `rᵀA[:,j]`, `xᵀB[:,j]`, `rᵀC[:,j]`와 독립 B 접힘을 검사한다. 원래 요청은 열 방향으로 추가 RS 부호화를 하고, 인증된 소수의 행 위치만 열어 **이 전체 열 입력과 그에 따른 회로 비용을 줄이는 것**이다. KZG로 행렬곱 전체를 다른 프로토콜로 증명하는 작업은 이 목표와 다르다.

## 소수 행으로 바로 대체할 수 없는 두 이유

1. **임의의 `xᵀB`는 `K` 미만의 열 평가값으로 결정되지 않는다.** 열 방향 RS 코드의 차수 제한이 완벽하게 검증돼 있어도 마찬가지다. 임의의 서로 다른 표본 위치 `u₁,…,uₜ` (`t<K`)에서 `h(T)=T^(K−1−t)∏(T−uᵢ)`를 고르면, `h`는 모든 열린 위치에서 0이지만 최고차 계수는 1이다. `x=eₖ₋₁`이면 원래 B 열과 `B+h`는 모든 sparse opening이 같고 `xᵀB`는 1만큼 다르다. [실행 테스트](../../crypto/columnrs_sparse_lower_bound_test.go)는 `K=8`, `M=16`, `t=1..7` 각각의 반례를 만든다. 일반적인 `x`에는 별도 내적 증명, sumcheck+다항식 opening, 또는 전체 B 열이 필요하다.
2. **Merkle root와 sparse opening만으로 열 방향 RS 저차성은 보장되지 않는다.** 기존 [격자 oracle 실험](COLUMN_RS_SAMPLING_PILOT_KO.md)은 값의 인증까지만 한다. 악의적인 증명자가 임의의 격자를 커밋할 수 있으므로 FRI/Brakedown 계열의 저차성 증명, 다른 sound한 PCS, 또는 검증자가 전체 데이터를 읽는 방식이 추가돼야 한다.

또한 `r`을 길이 `M=2K` 수직 부호 영역의 한 위치로 바꾸면, 잘못된 행렬곱을 한 번의 접힘이 놓칠 최악 확률은 약 `1/2`다. 독립 반복으로 약 128비트를 목표로 하면 수직 행 위치를 대략 128개 사용해야 한다. 이는 원래 전체 필드 challenge의 soundness와 다르다.

## Groth16 연결에 대한 판정

다른 브랜치의 `LAMPKZGLinkCircuit` 같은 KZG 연결은 이 목표를 구현하지 않는다. 소수 행 opening만을 기존 `LAMPCircuit.ColsEncABC`의 전체 열 대신 넣으면 위 반례를 받아들이므로, **sound한 Groth16 연결로 주장하거나 메인 회로를 수정해서는 안 된다.** 검증 가능한 연결을 만들려면 먼저 (a) 열 방향 저차성 증명과 (b) `xᵀB`의 별도 증명 관계를 명세하고, 그 두 검증기를 원래 LAMP transcript 및 Groth16 공개 입력에 묶어야 한다.

가능한 하이브리드는 B 열 전체를 유지하고 A/C의 접힘만 sparse opening으로 바꾸는 것이다. 그러나 수직 저차성 증명과 반복 challenge 비용은 여전히 필요하다. `K=4096`, 수직 부호율 `1/2`, 반복 128회라면 열당 A/C sparse 값만 `256`개가 되고 B의 길이 `4096` 벡터는 남는다. 기존 `3K=12,288` 값 대신 적어도 `4,352` 값이며, `xᵀB` 계산은 반복마다 필요하다. 이 수는 **낙관적 입력 개수**일 뿐 Merkle 경로, 저차성 증명, 벡터·코드워드와 Groth16 비용은 제외한다.

이 하이브리드를 세로 FRI 부호율 `1/8`로 구현해 네이티브 FRI 검사와 Groth16 회로를 연결한 [연구용 파일럿](SPARSE_FRI_GROTH16_PILOT_KO.md)이 있다. B 전체 열은 그대로 사용한다. 큰 행렬 실행은 표본 수가 너무 작아서 논문용 보안·성능 비교가 아니다.
